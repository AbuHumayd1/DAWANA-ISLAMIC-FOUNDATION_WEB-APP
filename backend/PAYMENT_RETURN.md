## Grant and verification flow

1. After initialization succeeds and before exposing its checkout link, React
   calls `POST /api/v1/dic/orders/<order-uuid>/payment-return-grant/` with the
   existing order bearer token, fresh CSRF token and session cookies.
2. The backend checks that bearer, then stores a two-hour order-bound grant.
   Its authority is bound to the validated server-side Django session using a
   keyed SHA-256 digest and to the current order access-token digest. No raw
   bearer, session key or grant is returned or written to browser storage.
3. The existing Secure, HttpOnly, SameSite=Lax, host-only session cookie is
   shared by same-origin tabs. Django's database session backend is required.
   Development retains its existing local cookie settings; production and
   staging retain their existing Secure cookie configuration.
4. The callback sends the Paystack reference as an untrusted hint in the body
   of `POST /api/v1/dic/payments/return/`, with cookies and fresh CSRF. Unknown
   references never fall back to another registration. Both new endpoints are
   also protected by the staging tester gate when enabled; tester membership
   alone does not grant order access.
5. Cookie grant, expiry, revocation, bearer rotation and order binding are
   validated. If the order is not paid/refunded/cancelled, its existing attempt
   is verified using the same settlement service as manual verification and
   signed webhooks. This route never initializes or retries a payment.
6. Paid status is read from PostgreSQL. The confirmation URL contains only a
   public order UUID and can be refreshed while its return grant is valid.
   Every retrieval reauthorizes and reads backend state; cached drafts and URL
   payment statuses never confirm payment. Pending, failure, reconciliation
   and provider outages do not produce a success screen.

Without a hint, the return page lists up to 50 recent authorized registrations
for selection; listing does not call Paystack. Saved per-order confirmation
links continue to address older grants within their expiry. Payment return has
its own throttling scope (`dic_payment_return`, default 60/hour), so browsing
confirmation pages does not consume the manual-verification throttle budget.
Responses are private/no-store. Grants are in separate rows with a unique
order/session constraint, so simultaneous orders cannot overwrite a grant list.

Expiry is deliberate: this is persistent retrieval across refresh/navigation,
not permanent public access. Logout/deletion/expiry of the Django session,
grant revocation, order access revocation, or bearer rotation invalidates access.
An authorized current bearer can renew an expired grant; it cannot restore a
revoked grant. Expired grant rows retain no raw credentials and can be removed
later under an approved retention policy; expiry is enforced without cleanup.

## Contact recovery and old checkouts

The existing contact/OTP recovery routes remain unchanged. A successfully
restored order bearer establishes a new return grant before the frontend offers
a persistent status link. No OTP is simulated. If the channels API reports no
operational delivery channel, the return page accurately directs the user to
the registration team and warns against registering or paying again.

Staging email delivery is normally disabled/sandboxed; this implementation does
not enable it or alter its recipient allowlist. A different device or a browser
with expired cookies requires genuine contact verification or separately
authorized staff assistance. Never substitute tester login for proof of order
ownership. Existing checkouts opened before rollout have no new return grant;
their original tab can establish one during manual verification, or their owner
must use the existing recovery process. No existing attempt is rewritten.

## Migration and rollout (approval required; not performed locally on Render)

`0017_payment_return_grants` creates only the new grant table and indexes. It
does not change or backfill existing orders, attempts, settlement evidence or
pricing. Apply it during an approved backend rollout before using the new
endpoints. Then deploy the matching frontend and verify the callback value and
SPA/proxy routing above. No production settings changes are part of this work.
The callback change affects subsequently initialized checkouts; do not assume
already-issued Paystack checkout URLs adopt a new callback value.

## Local regression checks

Use development settings and an isolated PostgreSQL database whose test name
starts with `test_`. Never run these commands against Render.

```text
python manage.py test dic.test_payment_return dic.tests.PaymentApiTests dic.tests.ConcurrentPaymentSettlementTests dic.test_recovery dic.test_staging_tester_access dic.test_paystack_diagnostics --keepdb --noinput --testrunner=dic.test_payment_return.CallbackRegressionRunner
python manage.py check
python manage.py makemigrations --check --dry-run
```

The focused runner clears **local-memory** throttle history before each test,
while preserving rate limits and assertions within each test. The old combined
suites otherwise share DRF throttle history across independent fixtures and
produce unrelated HTTP 429 failures. The runner refuses a persistent cache.
All provider requests and OTP deliveries are mocked; no Paystack payment occurs.

Frontend checks: `npm.cmd test`, `npm.cmd run lint`, `npm.cmd run build`.
Run these before starting Vite browser checks to avoid conflicting dependency
optimizer caches. Start Vite on `127.0.0.1:5178`, then run:

```text
node scripts/check-payment-return.cjs
node scripts/check-registration-ui.cjs
```

These scripts require installed Playwright and Chrome; `PLAYWRIGHT_MODULE_PATH`
may point to an existing installation. All API calls and non-local traffic are
intercepted. Browser fixtures model local HttpOnly cookies; backend tests assert
the staging/production Secure cookie flags and real CSRF/session authorization.
Real staging browser/cookie behaviour remains a post-deployment acceptance check
under separate approval. No automated test initiates a Paystack transaction.
