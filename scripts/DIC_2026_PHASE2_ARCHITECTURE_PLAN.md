### Current identity and duplicate behavior

`_create_order()` provides UUIDv4 request idempotency and payload fingerprinting, but creates a new Participant for each participant payload in a genuinely new order. It does **not** establish that two name/phone/DOB submissions are the same person. `CampEnrollment` uniqueness protects the same participant UUID in the same edition; it cannot deduplicate different UUIDs representing one person. Multiple sources for one participant trigger existing eligibility/source review. Reusing an idempotency key also rotates the existing order access token: assisted retries must not accidentally invalidate the payer's recovered session.

Name, phone, family email or age band must not become an automatic unique person key. A family can share contact details; names can coincide. Assisted intake should search existing candidates, explicitly verify identity, reuse the UUID where justified, and resume an existing unpaid order instead of creating another. Confirmed paid enrollment should stop a second paid registration for that known person/edition. Ambiguity requires authorized review, not an automatic merge or token disclosure.

Order creation already prepares an internal CampEnrollment before payment. That identifier is not proof of paid admission or an active QR. Booking recovery/portal access can support an unpaid customer's checkout while active ID/admission eligibility remains subject to trusted payment checks. Preserve this distinction rather than disabling the payer's recovery path or treating an internal enrollment as arrival eligibility.

## 3. Proposed implementation

### 3.1 Participant classification, admission and residence

Keep existing Participant UUIDs as canonical person identities and CampEnrollment as the unique edition identity. Introduce an independent **edition participation category**, not a replacement billing category or Django role. Suggested controlled codes, subject to approved naming: regular camper, tutor/instructor, guest lecturer, invited stakeholder, invited guest/visitor and explicitly approved other category. Multiple descriptive roles may coexist for one person; they must not create multiple enrollments or automatically waive an existing registration charge.

Proposed supporting-app models (names provisional):

- `ParticipationCategory`: edition, stable code, label, enabled state; policy configuration references with approval/audit. No invented fee or automatic staff entitlement.
- `AdmissionGrant`: existing participant + edition, category/roles, payment/admission basis, residential/day-visitor designation, validity window, approval/revocation status, approved-by/at, reason and evidence reference. Use one active invitation admission per person/edition with versioned changes, rather than a new person per visit. Keep billing basis separate from descriptive category: “father” does not inherently mean exempt, and a tutor who paid must not be silently reclassified as free.
- Optional approved visit windows, only if needed: allowed attendance dates/times under the same grant. Actual repeated arrivals/departures remain the existing physical movement records, not a parallel visit ledger. Define windows and a staffed exception procedure explicitly; do not invent dates/curfews.

Target enrollment extension: preserve existing non-null registration sources; permit an approved invitation admission **as an alternative source**. Proposed `CampEnrollment.source_item` nullable plus an `admission_grant` FK, with a DB XOR constraint (exactly one) and service checks ensuring matching participant/edition. Existing rows retain their source item and participant number. A grant must not be attached to an existing paid-source enrollment as a way to bypass unpaid/reconciliation restrictions; conversion/cancellation of an existing commercial registration needs a separate explicitly approved policy.

Eligibility has two explicit source branches:

1. **Registered camper:** existing trusted paid-registration eligibility unchanged.
2. **Invited/exempt admission:** approved active unrevoked grant, identity/age/safeguarding/residential conditions and permitted visit window. Label as authorized invited/exempt, never verified paid. No successful/fake/zero-value Paystack evidence is created.

Reuse DigitalIDIssue and existing scanner/check-in/movement services after source-aware authorization is implemented. QR payload stays an opaque credential; no DOB/category permission is encoded as authority in the QR. Existing directory/search, printing, check-in, movement manual lookup and source-review queries must include authorized invitation enrollments, not only RegistrationOrderItems. Distinguish receipt/payment totals from eligible people, residential occupancy, visitors and physical presence in every report.

Residence is independent of role/admission basis. Day visitors must not consume residential allocations. Existing `House.Purpose.FATHERS_AND_ADMINS` is available as a concept, but `housing_policy.validate_occupant` currently holds dedicated/nonparticipant accommodation for committee review. A category label must not bypass that hold or invent accommodation capacity. Explicit housing eligibility can later admit approved residential invitees; **do not change `paid_participants()` to count them as paid**.

Minimal invitation intake must be approved separately: name plus reliable identity/contact-or-host reference and residency/window information; sex/age evidence where safeguarding/housing requires them. Do not collect invented height/weight, email, occupation or birth date just to satisfy the existing rich camper model. Core optional-field changes for guest applicability are part of the migration gate below; existing paid-camper required fields remain enforced by their serializers/services.

Participant classifications never create auth.User, set is_staff/is_superuser, join groups or grant Operations permissions. Existing lecturer/publicity records may be explicitly linked to the person after review, not auto-merged by name. Guest portal capability data may be prepared, but **Phase 3 portal login, claims and role-aware UI are not implemented in Phase 2**. Some day visitors may need no portal at all.

### 3.2 Age/DOB privacy target

Target core DOB representation: retain existing exact DOBs; allow null only through an approved mutually exclusive age-evidence mode. Proposed supporting `AgeEvidence`/assessment: participant, `exact_dob` / `adult_band` / `review_required` mode, band, as-of reference date, asserted/verified/rejected state, reviewing official/time, method and minimal evidence reference, revision/supersession reason. The DOB value stays in the controlled identity field, not duplicated across assessment notes.

Adult bands: **18–24, 25–34, 35–44, 45–54, 55–64, 65+**. Never create a synthetic 1 January birth date, band midpoint or fake measurements. A self-declared adult band is an assertion, not automatic verified adulthood. Where exact DOB is mandatory, including minor registration under the proposed default, require it; a controlled adult verification process can establish adulthood/band evidence without retaining exact DOB. Committee approval is required for accepted methods and responsible reviewers.

Exact-age helpers remain exact and cannot return a guessed integer for band-only data. Add a separate policy evaluator returning eligible/ineligible/review plus evidence provenance. Evaluate range proof against the specific threshold/reference date, conservatively accounting for birthday changes between assessment and the relevant date. A band declared at registration is not automatically the same band at camp arrival. If confidence/range cannot establish the rule, require review or exact information. No age mode grants guardian/collection authority.

Backward compatibility: existing DOB values and old immutable registration snapshots are not erased or rewritten. New paid-order snapshots explicitly record age mode/provenance without copying reviewed identity documents. Historical retention/redaction is a separate approved decision. Paid eligibility/settlement still depends on the existing provider evidence; age review does not mark a payment successful.

### 3.3 Assisted registration using existing Paystack flow

Proposed route: `/dic/operations/assisted-registration`, under the existing staff session/CSRF architecture, with a distinct proposed assistance permission. No separate login. Intake remains full required camper registration (or the subsequently approved adult-band alternative), with primary contact belonging to the camper/verified responsible registrant—not the officer.

Reuse `_create_order` and its validation/pricing through a bounded shared application service rather than copying it or server-forwarding HTTP to the public endpoint. The public behavior must remain compatible. Staff cannot submit payment status, amounts as final authority, callback proof or an exemption flag through assisted camper intake.

Proposed `RegistrationAssistance` association: staff actor, order, edition, source=assisted, creation time, idempotent request identity/fingerprint and audit reference. Create the order and association atomically. Repeated assisted requests return the same existing association/reference without unnecessarily calling the existing retry branch that rotates order access tokens. A reused key with changed data is a conflict. Check known-person/current-edition registrations under locks; resume a pending order, reject duplicate known paid enrollment and route conflicts to review. Never auto-merge similar names or infer adult identity from a shared phone.

**Smallest safe payer handoff:** give the payer their booking reference and use the existing primary-contact recovery/OTP + restore-existing-order flow on the payer's own device. Do not return/persist an order bearer token in the officer's shared browser. The recovered order is the same order, not a second registration. The payer's device establishes its own existing PaymentReturnGrant session, reviews accepted pricing and opens existing Paystack checkout. Reusing existing recovery avoids inventing another authentication architecture. Verify mobile campsite contact-delivery availability first; if delivery is unavailable, assisted cross-device payment is blocked until an approved existing-channel fallback is agreed—not marked paid by staff.

Browser return grants are cookie/session bound. Forwarding an officer's browser storage or assuming their callback session works on a payer's phone is unsafe/incompatible. Officer monitoring should expose only their authorized assistance record's order/reference/payment status through a scoped Operations endpoint; it must not reveal payer tokens, PINs, OTPs or full booking ownership. Do not record payment credentials/screenshots as evidence of successful Paystack settlement.

Pending/failed/cancelled/unknown-initialization/repricing/retry states remain existing PaymentAttempt/order states. Reuse an unresolved provider attempt; do not initialize a second charge while reconciliation/unknown outcome is unresolved. Trusted provider verification/webhook alone sets confirmed/paid. Redirects and screenshots never confer eligibility. After verified payment, reuse existing enrollment/ID eligibility and explicit staff ID issuance; the existing system does not automatically issue an active QR merely because payment succeeded. The payer's existing participant access remains booking/contact scoped.

On-site registration outside configured registration windows is a business decision: `_registration_is_open` currently blocks it. Do not silently override closed registration or expired pricing. If an exception is required, specify and approve its permission, reason, pricing rules and audit before adding it.

### 3.4 Academic class relationship, without Phase 4 timetable work

Propose edition-scoped `AcademicClass` (stable code/name, programme/track, optional venue reference, active state), a subject catalogue/class-subject relationship if approved subjects are available, and audited `ClassPlacement` relating an existing enrollment/person to a class. Placement stores proposed/confirmed state, assessment basis/level, assigning official/time, reason and supersession history. Tutor links point to explicitly approved participant/lecturer identities, not arbitrary auth privileges.

Do not equate house with class. Do not assume academic status determines learning ability. Existing statuses are Primary Student, Secondary Student, Tertiary Student, Graduate/Completed Tertiary and Not Currently in School; the final programme labels/levels need confirmation. Rules can suggest placement using academic status, safely established age and approved assessment evidence, but remain unpublished/inactive until approved. Authorized manual placement/adjustment remains possible and audited. Agree whether one class per programme/track or multiple concurrent classes are allowed before setting uniqueness constraints.

Prepare relationships and read contracts for eventual assigned class, subjects, venue and published schedule revision. **Do not build schedule recurrence, timetable editing/publishing/downloads or the Phase 3 portal interface now.** Phase 4 owns timetable implementation. No fictitious subjects, classes, instructors or placements are seeded.

### 3.5 Permission and audit proposal

Reuse active staff + Operations authorization, with separately approved permissions for assisting registrations, viewing/managing admissions, approving/revoking invited admission or fee exemption, reviewing age evidence/viewing sensitive identity, and proposing/confirming academic placements. Intake must not imply fee-waiver/age approval; participant category must not imply staff access. Existing movement groups/permissions stay unchanged. Names and any new least-privilege groups require approval before grants.

Audit intake/order association, explicit person reuse/review, admission approval/revocation/category/residence changes, age review/supersession, and class-placement changes with actor/server time/edition/target/reason and non-sensitive before/after values. Preserve finance and movement audit semantics. No raw DOB/document, payment credential, order token, OTP or QR secret in general audit details. Record privileged sensitive reads under an approved access policy; routine broader Operations audit access must not bypass new sensitive domains.

## 4. Migration and data-safety strategy

### Hard migration gate

The target design requires genuine changes to existing `dic.Participant` and `dic.CampEnrollment`: nullable/conditional DOB and guest-applicable fields, alternative admission source, validation and constraints. Adding only a sidecar age-band table cannot make the existing non-null DOB or mandatory paid registration source optional. Likewise, merely adding a zero-fee billing category does not supply trusted payment evidence or minimal guest intake.

`dic.0027_feedback_welfare` is an unapplied child of dic 0026. A normal next dic migration descending from 0027 would pull in postponed schema. A second dic leaf beside 0027 creates a migration conflict; a merge depending on both does not solve postponement. **Do not generate/apply such a migration or smuggle a core-field alteration into another app with unreviewed RunSQL/state edits.** Core model ownership and all cross-app migration state must remain consistent.

Recommended sequence:

1. Preserve historical migrations and existing participant/order/payment/ID data. Obtain a separately reviewed resolution of the pending dic migration lineage before any core-field migration. If migration-owner restructuring or relocation of never-applied postponed work is considered, first prove its applied status across every environment and review that as explicit migration work; this report does not authorize deleting/renaming/rebaselining 0027.
2. A new supporting app such as `dic_participation` may safely define additive categories, admission grants, age assessments, assistance associations and class structures against dic 0026 without depending on feedback/welfare. Keep its initial dependency direction acyclic: grants reference existing Participant/Edition; the future core enrollment source extension can depend on those grants. Later supporting revisions may reference the extended enrollment. Final app boundaries/names await approval.
3. Supporting tables alone are **not permission to ship** band-only registrations or invited enrollments. Hold those flows until the explicit core migration and all consumer changes pass review. Assisted registration retaining current exact-DOB requirements can be implemented independently after architecture approval, using additive audit association and unchanged payment rules.
4. Existing enrollment UUIDs/participant numbers, sources, orders, price snapshots, payments, ID issues, check-ins and movements remain unchanged. New existing-person/edition uniqueness and concurrency protections must be tested against legacy multi-source cases before any backfill. Do not auto-create invited/grant roles from house purpose, lecturer name, staff role or booking category.
5. No blanket migration, schema command or backfill is prepared in this planning task. Runtime graph/model-state validation is mandatory once approved migrations are designed; target plans must explicitly exclude 0027. Use fresh isolated PostgreSQL fixtures with no real provider/delivery calls, not dawana_dev or the protected OTP database.

Rollback must be planned before writes: disabling new capability is safer than deleting admissions/age evidence already referenced by IDs or movements. Converting DOB to non-null again is impossible without real exact DOB for every band-only row; no reverse migration may fabricate dates. Preserve immutable paid snapshots/audits and backup/recovery evidence. Decide revocation behavior for invitation QR issues, pending class placement and current presence; never rewrite an already recorded physical movement to hide an admission change.
